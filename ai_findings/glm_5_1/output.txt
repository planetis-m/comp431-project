F-001: Chunked body unbounded — maxBody not enforced during chunked transfer
  Type: DoS
  Location: asynchttpserver.nim:295-331
  Input: POST / HTTP/1.1\r\nTransfer-Encoding: chunked\r\n\r\nFFFFFF\r\n...<16MB>...\r\n0\r\n\r\n
  Root cause: The Content-Length path (line 288) checks `contentLength > server.maxBody`, but the chunked encoding path (line 295-331) has no analogous check. `request.body.add(chunk)` at line 324 accumulates without any size limit. An attacker can send unlimited data via chunked encoding, exhausting server memory.
  Exploitability: Remote, no auth needed, high impact — unbounded memory consumption leading to OOM
  Classification: CONFIRMED

F-002: parseHexInt overflow in chunked encoding yields negative bytesToRead
  Type: logic
  Location: asynchttpserver.nim:311
  Input: POST / HTTP/1.1\r\nTransfer-Encoding: chunked\r\n\r\n7FFFFFFF\r\n...\r\n0\r\n\r\n
  Root cause: `parseHexInt` delegates to `parseutils.parseHex` which documents "It does not check for overflow. If the value represented by the string is too big to fit into number, only the value of last fitting characters will be stored." A hex string like "7FFFFFFF" (2^31-1 = max int32) or "80000000" (overflows int on 32-bit) results in undefined/wrapped values. On a 64-bit system, a very large hex value produces a huge positive `bytesToRead`, which then calls `client.recv(bytesToRead)` — potentially trying to receive gigabytes. On a 32-bit system, overflow wraps negative, and `recv` with a negative count has undefined behavior. Combined with F-001, there is no body size guard.
  Exploitability: Remote, no auth needed, DoS via massive recv or undefined behavior
  Classification: LIKELY

F-003: Split-on-space request line yields wrong method/URI/protocol with extra spaces
  Type: logic
  Location: asynchttpserver.nim:218
  Input: GET  /path  HTTP/1.1\r\n (two spaces between each part)
  Root cause: `split(' ')` produces empty strings for consecutive spaces (per strutils split semantics). With `"GET  /path  HTTP/1.1"`, split produces `["GET", "", "/path", "", "HTTP/1.1"]`. The case statement at i=1 receives `""` (empty string) for URI, i=2 receives `"/path"`, i=3 receives `""` and hits the `else` branch returning Http400. A valid per-RFC request line with multiple SP characters is rejected. Conversely, `"GET /path HTTP/1.1 extra"` (4 parts) also hits `else` at i=3 — but that is a malformed request. The real issue is that valid requests with extra spaces (some HTTP implementations tolerate this) are broken.
  Exploitability: Remote, no auth, causes false rejection of requests — low security impact but protocol non-compliance
  Classification: CONFIRMED

F-008: Header with no colon produces empty key — stored in headers table
  Type: logic
  Location: asynchttpserver.nim:264, httpcore.nim:244-262

  Root cause: `parseHeader` at httpcore.nim:251 does `parseUntil(result.key, ':')` which returns 0 characters if ':' is the first char, or returns the whole string if no ':' exists.   Exploitability: Remote, no auth, header injection/pollution — could confuse application logic that iterates headers
